# 週次の記事生産（自動セッション用の手順書）

月・水・金の朝8時（日本時間）に、自動で起動するセッションがこの手順に従う。
1回の起動で書く下書きは1本。CLAUDE.md 6節の上限（週4〜5本）を超えないため、週3本までとする。
（2026-09-23 に週1回から週3回へ変更。運営者の了承済み）
**目的は公開ではない。運営者の手が空いたときに、5〜10分で公開できる状態の下書きを作って置いておくこと。**

## 絶対に守ること

1. **`TODO:実体験` を自分で埋めない。** 埋めていいのは運営者だけ（CLAUDE.md 4節）
2. **記事を main にマージしない。** 下書きはブランチに置く。公開の判断はディレクターと運営者が行う
3. **公式ページに接続できない数値は書かない。** `TODO:数値` として空欄で残す（この環境は各モールの公式ドメインへの接続が遮断されている）
4. 迷ったら進めず、報告に「ディレクターに確認したいこと」として書く

## 手順

### 1. 何を書くか決める

`knowledge/記事の企画リスト.md` の上から、状態が `未着手` の企画を1つ取る。
取ったら状態を `下書き中` に更新する。

企画リストが空、または全部着手済みなら、記事を書かずに次を行う。
- 既存記事を読み、`verified` が90日以上前のものを洗い出す
- 企画の候補を3つ提案し、企画リストに `未着手` で追記する
- そこで終了し、報告する

### 2. 素材を集める

`knowledge/体験バンク.md` を**必ず先に読む。**その企画に使える実体験が貯まっていれば、それを使う。
**貯金があるなら、運営者に聞き直さない。**

足りない一次情報は `research/` を見る。なければリサーチ担当（researcher）に依頼する。
公式ページに到達できなかった数値は、推測で埋めず `TODO:数値` にする。

### 3. 書く

**構成より先に切り口を決める（CLAUDE.md 6節）。** 検索者の問いを1文で書き、
タイトルをその答えにする。調査中の発見は本文の1節に置き、タイトルの軸にしない。
運営者が示している理由や仮説は、前提として扱う。


SEO担当（seo）→ 記事作成担当（writer）→ エディター（editor）→ 校正担当（proofreader）の順に回す。
各担当の定義は `.claude/agents/` にある。サブエージェント同士は会話しないので、
このセッションがハブになって受け渡す。

体験バンクから使った話は、`knowledge/体験バンク.md` の該当項目に「使った記事」を追記する。

### 4. 空欄を質問に変える

記事に残った `TODO:実体験` と `TODO:数値` を、運営者がそのまま答えられる問いの形に直し、
`knowledge/質問キュー.md` の**先頭に**追記する（次の日次質問で優先的に聞かれるようにするため）。

### 5. 置いて、知らせる

- ブランチ `claude/draft-<slug>` を作り、下書きをコミットして push する
- `node .github/scripts/generate-site.js` は実行してよいが、**記事を main へマージはしない**
- 企画リストの状態を `回答待ち` に更新する
- **`knowledge/` の更新（企画リスト・質問キュー・体験バンク）は main に直接コミットして push する。**
  他の定期実行は main を読むため、ブランチにだけ置くと、同じ企画をもう一度書いたり、
  新しい問いが質問キューの先頭に来なかったりする（2026-09-24 に実際に起きた）。
  `knowledge/` はサイトに出ないので、main に入れてよい
- 報告には次を必ず書く
  - 記事のタイトルと slug、ブランチ名
  - 残っている空欄の一覧（何を誰が埋めるか）
  - 運営者に答えてほしい質問（3つまで。多いと答えられない）
  - 公開までに他に必要な作業

## 報告の形式

報告は `PushNotification` で運営者に届く。**運営者が通知を読んだだけで、次に何をすればいいか分かること。**
「何をすればいい？」と聞き返させたら、その報告は失敗である。

- **通知の1文目は、運営者にお願いしたいこと**にする。やることがなければ「今回はやることはありません」と書く
- お願いごとには、次の3つを必ず添える
  - 答え方（通知・このセッションに返信する／毎日の質問で届くのを待てばよい、など）
  - 急ぎかどうか
  - 何もしなかった場合にどうなるか
- 公開の判断を仰ぐときは、選択肢を並べ、それぞれ運営者が何をすることになるかを書く
- 通知には専門用語（ブランチ、slug、TODO、push など）を使わない。CLAUDE.md 12節の言い換えを使う
- 作業の記録（切り口・空欄の一覧など）は、お願いごとの**後ろ**に置く

```markdown
## あなたにお願いしたいこと
（1文目。やることがなければ「今回はやることはありません」）
1.（具体的な問い／判断）— 答え方：（…）／急ぎ：（はい・いいえ）／何もしなければ：（…）
2.
3.

## 公開について
（選択肢と、それぞれで運営者がすること）

## 今週の下書き
（タイトル。専門用語を使わずに、どの記事を広げたものかなど）

## 切り口
- 検索する人の問い：（search_intent を1文で）
- タイトルの理由：（title_reason）
- 差別化：（書き方でどう出したか）

## 残っている空欄
（運営者の体験が入る空欄と、数値の空欄。何を書く欄か）

## ディレクターに確認したいこと
（判断が要る点。なければ「なし」）

## 作業の記録（運営者は読まなくてよい）
（slug／ブランチ名／コミット。再開するときのため）
```
