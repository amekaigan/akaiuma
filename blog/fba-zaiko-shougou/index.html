月末に、自社のエクセルで「先月末在庫＋今月の納品数－出荷数」を計算します。その数字がAmazonの月末在庫と合わない月が、たまにあります。毎月ではないので、入力ミスやSKUの取り違えを探しても見当たらず、原因の分からない差が残ります。筆者にとって、在庫の月末の数字がずれていた瞬間は、かなり憂鬱でした。

筆者の場合、差の原因は数え間違いではなく、Amazon側の在庫の状態でした。今のところ把握しているのは、紛失・発見・倉庫間移動中・顧客返品の4つです。

FBAの在庫元帳をもとにエクセルで計算式を組めば、月末在庫を照合できます。紛失中の在庫は、筆者は「ある」扱いのまま持ち、補填などの処理がされた時点で「なし」にしています。

この記事が扱うのは、FBAに預けた在庫の月末の数字だけです。自社倉庫とFBAを併用したときに在庫の定義がずれる構造は、在庫が合わない原因を、定義と情報共有の面から書いた記事に任せます。FBAに寄せる判断や手数料は、FBAに寄せて在庫管理がどう楽になるか、その条件を書いた記事にあります。

月末在庫の差は、数え間違いだけではない

自社の式とAmazonの在庫を同じSKUで並べる

照合の出発点は自社側の式で、先月末在庫に今月の納品数を足し、出荷数を引いた結果を、Amazonの月末在庫と同じSKUで並べます。

ここで毎月一致していれば、照合は要りません。困るのは、たまに合わない月があることです。合わないSKUが出たとき、真っ先に疑うのは自分の入力ですが、筆者の場合は探しても数え間違いは見つかりませんでした。

数え間違いを探しても見つからないとき

数え間違いが見つからないのに差が残るなら、次に疑うのはAmazon側の在庫の状態です。

次の節で、何が差を作るのかを書きます。

筆者が把握している4つの在庫状態

筆者が今把握している差の原因は、紛失・発見・倉庫間移動中・顧客返品の4つです。この4つは筆者の経験の範囲で、Amazonの公式の分類ではありません。ほかにも原因がある可能性があり、この4つがすべてだとは言えません。

紛失

Amazonの在庫の状況には「紛失」があります。Amazonが在庫を紛失した状態です。数か月後に、商品代金が補填されることもあれば、発見されることもあります。

発見

紛失中とされていた在庫が、あとから見つかる動きです。見つかるまでの期間は、筆者の経験では数か月かかることがあります。

倉庫間移動中

倉庫間を移動している最中の在庫も、月末の数字に差を出す原因として把握しています。どの倉庫からどの倉庫への移動かによって、差の出方は変わります。自社倉庫とFBAを併用している場合に、送った在庫がどちらの数字にも入らずに浮く仕組みは、自社倉庫とFBAを併用したときの在庫のずれを扱った記事で書いています。

顧客返品

お客様から返品された商品も、月末の数字に差を出す原因のひとつです。FBA倉庫での返品の扱いは、同じ在庫のずれを扱った記事でも触れています。

自社の式に入っていない動き

自社の式が見ているのは、納品と出荷だけです。たとえば返送や所有権放棄のように、FBAから在庫を引き上げる動きは、納品にも出荷にも入りません。こうした動きが差になりうるのか、在庫元帳でどう表示されるのかは、この記事の執筆時点では未確認です。

在庫元帳と自社の式で、差のSKUを絞る

在庫元帳について、Amazonの公式のAPIドキュメント（2022年1月時点の版）は、「在庫の銀行明細のようなもの」と説明しています。通帳が預金の残高を入出金の履歴で説明するように、在庫の残高を、動きの履歴で説明するレポートということです。ただし、この説明はAPI向けのもので、日本のセラーセントラルの画面の現行の文言と同じとは限りません。

出典：Amazon Selling Partner API ドキュメント「Report Type Values」（amzn/selling-partner-api-docs の2022年1月4日時点の版）／2026年10月1日確認。「Inventory Ledger Report is like a "bank statement" of your inventory」の部分を参照。

照合は、次の順に組み立てます。

  1. FBAの在庫元帳を、月末を含む期間で出します。
  2. エクセルに貼り、自社の式の結果と同じSKUで並べます。
  3. 差が出たSKUだけを絞り込みます。
  4. 絞ったSKUの動きを、紛失・発見・倉庫間移動中・顧客返品のどれに当たるかで仕分けます。

在庫元帳の出し方（画面のどこから、どの表示で、どの期間を指定するか）と、画面の項目名は、セラーセントラルの表記が変わることがあります。そのため、実際に出す前に、公式のヘルプと画面の現物で確認してください。

紛失中は「ある」、補填が出たら「なし」

ここから先は、筆者の運用の話です。会計上どう扱うのが正しいかは、この記事では断定しません。

紛失中の在庫を数えるかどうかも、何を1個として数えるかを先に決めておく考え方のひとつで、自社で決めておく項目です。

実際にやってみて分かったこと

在庫がどうしても合わない部分が、Amazonの在庫の状況にある「紛失」でした。つまり、Amazonが紛失してしまったということです。これは数か月後に商品代金が補填されるかもしれませんし、数か月後に発見されるかもしれません。

このような場合、当店ではその在庫が「ない」という扱いではなく、普通に「ある」という扱いをしています。そして、補填なりの処理がされたタイミングで「なし」の扱いにしています。一見理不尽に思える、不可抗力的な事象が、たまに発生します。

なぜ「ない」にせず、「ある」のまま持つのか

紛失した在庫は、補填されるのか発見されるのかが、数か月たつまで分かりません。そのため筆者は、結果が決まるまで「ある」のまま持ち、処理がされた時点で切り替えます。

「なし」に切り替える合図

切り替えの合図は、補填などの処理がされたタイミングです。

発見されたときの戻し方

毎月の記録と、当てはまらないケース

月末に見る数字と、残しておく数字

毎月、次の数字を同じ形で残します。

  • 差が出たSKUの数
  • 差の個数の合計
  • 差を4つの状態に仕分けた内訳
  • 仕分けられなかった差の個数
  • 紛失中として「ある」のまま持ち越している個数
  • その月に補填・発見が出た個数

前月と並べて見るのは、数字の増減よりも、仕分けられなかった差が残っているかどうかです。4つのどれにも当たらない差は、数え間違いか、筆者がまだ把握していない動きのどちらかを疑います。

差がいくつなら問題、という線は、この記事では引きません。SKUの数や単価、扱う量によって、同じ個数の差でも意味が変わるためです。

そのため、毎月同じ形で記録を残して前月と並べ、動きのあった項目を見ます。金額で見たいときは、差の個数に仕入れ値を掛けた額も、同じ表に足します。

この方法が当てはまらないケース

  • 自社倉庫とFBAを併用していて、主な差が本社倉庫からFBAへの移動にある場合は、この記事の範囲を外れます。FBAに預けた在庫だけを見る照合なので、定義の側の話が先になります。
  • 自社側で「先月末在庫＋納品数－出荷数」を持っていない場合は、照合する相手がありません。先に数え方を決めるところからになります。
  • この記事は数量の照合です。差の金額をどう評価し、会計上どう処理するかは扱っていません。

まとめ：今月末にやること

次の月末は、この順で照合します。

  • FBAの在庫元帳を、月末を含む期間で出す
  • 自社の式の結果を、同じSKUで並べて、差が出たSKUを絞る
  • 差を、紛失・発見・倉庫間移動中・顧客返品に仕分ける
  • 仕分けられなかった差を、数え間違いか未把握の動きとして、別に記録する
  • 紛失中の在庫は「ある」のまま持ち、補填などの処理が出た時点で「なし」に書き換える
  • 差のSKU数・個数・内訳を、前月と同じ形で記録する

記録が前月と並べられるようになったら、最初に見るのは仕分けられなかった差です。ここが毎月残るなら、数え間違いか、4つ以外の動きのどちらかが差を作っています。
